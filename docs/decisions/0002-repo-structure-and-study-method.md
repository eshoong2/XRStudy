# ADR 0002: 저장소 구조와 학습 방식

- **상태**: 승인
- **날짜**: 2026-11-16

## 배경

여러 분야를 깊이를 나눠 공부하므로 전체 지도(로드맵)가 필요하다. 또한 이 공부의 목표는 프로젝트 완성이 아니라 **기술 이해와 수학 공부**이고, 주된 방법은 수학책 공부와 논문 읽기다.

## 비교한 대안: 저장소 구조

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 저장소 하나에 로드맵과 모든 코드 | 관리가 단순하다 | 구현 코드 하나만 따로 보기 어렵고 저장소가 비대해진다 |
| **B. 로드맵·노트 저장소 + 구현별 저장소** | 학습 기록과 구현이 각각 독립적으로 읽힌다 | 저장소가 여러 개가 된다 |
| C. 분야별 저장소 | 분야 구분이 명확하다 | 교양·보류 트랙까지 저장소로 만들기에는 과하다 |

## 결정

1. **B안**을 택한다. 로드맵·노트는 `XRStudy`, 이해 확인용 구현은 별도 저장소(첫 번째는 `SoftRasterizer`)로 둔다
2. 학습의 중심은 **수학책 공부와 논문 읽기**다. 코드 구현은 목적이 아니라 **이해를 확인하는 도구**로 쓴다
3. 논문은 3단계 읽기(Keshav)로 읽고, **6가지 질문**으로 판단한다. 트랙의 깊이에 따라 목표 읽기 단계를 다르게 한다
4. 각 단계의 완료 기준은 "구현 완성"이 아니라 **"이해 확인 질문에 노트 없이 답하고 유도할 수 있음"**으로 한다

## 이유

- 목표가 이해라면 완료 기준도 이해로 정의해야 한다. 구현 완성을 기준으로 하면 "돌아가게는 만들었지만 왜 되는지 모르는" 상태로 넘어갈 위험이 있다
- 그럼에도 구현을 남기는 이유는, 식을 코드로 옮겨 예상대로 동작하는지 보는 것이 이해했는지를 가장 확실하게 확인하는 방법이기 때문이다
- 노트와 논문 분석이 저장소에 쌓이면 그 자체로 학습 과정의 기록이 된다

## 결과

- `SoftRasterizer` 저장소는 주력 1단계를 시작할 때 만든다
- 로드맵의 문헌 서지 정보는 AI와의 대화로 정리한 것이므로, 읽기 전에 원문으로 확인한다
